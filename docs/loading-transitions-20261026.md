# 戦闘前後のローディング表示

提供済みの仮スチル6枚を元PNGのまま使用する。戦闘前は「森の街道」「遺跡への突入」「石橋の守護者」、戦闘後は「木陰で休憩」「仲間の手当て」「夕映えの帰路」。すべて1920×1080。画像対応と原本照合用SHA256は `godot/assets/loading/manifest.json`。宴会の画像は今回使用しない。素材は仮採用のまま扱う。

`main.update()` の `travel`（街道→配置）、`begin`（配置→戦闘開始）、`trial`（試用盤面）の前に戦闘前スチル、`finishBattle` / `retreat` / `endTrial` と結果画面から町へ戻る `acknowledge` の前に戦闘後スチルを表示する。戦闘セーブ再開も戦闘前、盤面から非戦闘セーブへ移るロードも戦闘後の対象。町の出発→街道、通常の売買やプレビューには表示しない。明示的な失敗応答時にも必ず解除する。

勝利が既存の確定結果文字列で確認できる通常終了は戦闘後3枚から選ぶ。敗北・撤退・試用終了・結果未確認の退出は、勝利後の休憩を示唆しない「夕映えの帰路」に固定する。絵は移行の背景であり、報酬やHP回復を表すものではない。ルール判定・乱数・報酬の処理はnativeを変更せず使用する。

独立UI RNGで選び、ゲーム進行乱数や他施設の表示乱数を消費しない。画像6枚は起動時preloadし、切替時にPNG decodeを待つことを避ける。元画像は各約4MB、合計約24MBで、texture常駐メモリも増える。これは継続描画負荷の最適化ではない。

`loading_screen.gd` は最前面CanvasLayer2048と全画面の入力遮断Controlを使用。比率を保つcover表示で、窓の比率によって端がトリミングされる。背景のクリック・キー・カメラ操作を遮断し、既存の子窓は遷移開始時に閉じる。WM_CLOSEの終了経路は維持する。

最初の実描画完了 `frame_post_draw` を待ってからengine処理へ進み、正規応答・自動到着処理・背景/NPC生成・試用文脈復帰を済ませた次の描画完了で解除する。`present()` の前に外すため既存の初手演出を覆わない。人工的な最低表示時間・入力待ちはない。高速なロードでは短く見える。headless検証時のprocess_frame待ちは実画面確認とは区別する。所有tokenで古い終了処理が新しいoverlayを消すことを防ぐ。

## 検証

- `python godot/tests/run_inventory_header_261020.py --evidence <checkout外のdir>` に `loading_screen_check` を追加。画像のハッシュ/寸法、通常入口、勝利2区間、敗北・撤退、試用復帰、失敗応答/接続終了、token、セーブ/乱数/報酬の整合を確認する。
- `godot/tests/loading_screen_gui.gd` はX11/XTest実操作。新規プロフィールの地図→出発→道選択→配置→開始、合成した正規検証済み勝利境界の終了、FHD/1180×812/960×540、背後入力遮断、残留なしを確認。証拠撮影時だけテスト側がengine busyを保持するが、製品には待ち時間を入れない。
- 検証時はBGM・ボイス・SEをOFF、個別XDG/保存先を使う。クラウドLinuxソフトウェア描画での確認は実GPU・Windows実UI・本人PCの確認と区別する。

## 今回の確認範囲

ローカル標準41/41、native23/23段階、専用loading144項目、実X11入力63項目、別担当の独立実画面82項目が成功。接続generation同owner/新owner、実X11 WM_DELETE_WINDOWによる待機中終了も最終12項目成功。終了試験の初回不一致は再現せず、同条件の再試験で成功した事実と区別して記録する。

クラウドllvmpipeで1回測った `load(main.tscn)` 開始〜初期キャンペーン・settle・first draw は約1.63秒（warm import cache、readback前、プロセス起動時間/本人PC値ではない）。初期texture monitorは約85.4MB、static約72.1MBでアプリ全体を含み、今回追加分だけのメモリ量ではない。6枚preloadによる常駐コストとの交換で、遷移直前の画像decodeを避ける。性能改善値や実GPUでのロード時間は未測定。
