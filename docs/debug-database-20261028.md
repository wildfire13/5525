# ローカル診断SQLite（実装・ローカル検証完了）

## 目的と保存先

別ウィンドウの最新200件表示を維持し、再起動後に調べる構造化イベントを `user://diagnostics/debug.sqlite` に保存する。`user://` はGodotの当該ゲーム用ユーザーデータ領域。マスタ `native/data/master.sqlite`、進行セーブ、ゲーム内の行動ログとは別物で、外部送信しない。「表示履歴を消去」は窓の履歴だけを消し、DB履歴は保持する。

製品ルール、乱数、報酬、セーブ、マスタ内容は変更しない。ソースを実行するdebugビルドでは記録を開始し、窓を開閉しても記録の有効性は変わらない。`NATIVE5525_DEBUG_DB_OFF=1` で永続記録を停止できる。releaseは `OS.is_debug_build()` の分岐で記録ノード、子プロセス、DB、キューを生成しない。既存別窓もreleaseでは生成しない。

## スキーマと記録範囲

- `sessions`: ランダムな起動識別子、固定build識別子、UTC開始/更新時刻、正常終了フラグ、最終シーケンス。
- `events`: セッションFK、単調シーケンス、操作相関番号、起動後経過ms、イベント種別、固定操作コード、成功/失敗、所要ms、安全な構造化データ、DB書込みUTC時刻。セッション＋シーケンスは一意で再送を二重登録しない。
- 要求開始/完了を同じ相関番号で結び、ファイル保存の準備、書込み、読込み、ゲーム状態への適用を区別。選択画面や確認の取消はUIイベントで区別する。
- 戦闘は匿名の人物番号、行動順、選択したスキル/付与部位/付与枠、CT、帰還使用済み状態を前後スナップショットとして保持。装備IDはセッションごとのsalt付き参照値とし、名称は保存しない。
- フレームごとの描画/演出要求やホバーの成功通信は保存対象にしない。演出を経て確定状態が変わる際は状態差を記録する。状態欄の5Hz監視は変化時だけで、200ms未満の全遷移を網羅するものではない。
- 人物名、保存ファイルのパス/本文、台詞、要求引数、例外文字列、認証情報は保存しない。GodotとPythonの両境界で、固定列・列挙値・上限付き数値/配列のみを受け入れる。

現在のbuild識別子は `89c4990+debug-store-v1`。正式な配布版を作るときは実際のbuildと一致する識別子へ更新する。ユーザー入力や任意の環境変数をバージョン文字列として記録しない。

## 上限と障害時

Godot側は最大256件の待ちキュー、1バッチ32件、通常200ms間隔で専用Python子プロセスへ非同期送信する。ゲーム要求は診断の完了を待たない。満杯では新しい診断を捨て、可能なら捨てた件数を記録する。DB側は最新20セッション/10,000イベント/構造化本文合計8MiB以内へ古い記録を整理し、ページ数でDB本体16MiBを上限とする。削除ページは再利用し、毎回VACUUMしない。

SQLiteはDELETEジャーナル、50msのロック待ち。ジャーナルは書込み中に別途必要で、DB本体上限だけを総ディスク使用量の保証とは扱わない。起動時には本体16MiB/各既存sidecar18MiBの過大ファイルを拒否する。破損・別用途のDB・過大ファイルを自動削除/置換しない。回復する場合はゲーム終了後に診断ファイルだけを退避する。マスタや進行セーブを退避対象と混同しない。

DB失敗・ロック・子プロセス応答失敗は永続記録だけを停止し、窓へ固定の停止案内を表示する。無制限の再試行はしない。二重起動は異なるセッションで共存し、競合時にもゲーム側を待たせない。別の稼働セッションを「クラッシュ済み」と決めつけない。

通常終了時は最大700msの範囲で未送信分と正常終了マーカーを保存する。強制終了/停電では、未flushキュー・処理中バッチは失われ得る。既にcommitしたDBの回復はSQLiteに委ね、`clean_closed=0` は「正常終了を記録できなかった」の意味で、クラッシュ原因の断定には使わない。全操作が必ず記録される監査証跡ではない。

## 調査方法

ゲームを終了した後、SQLiteの読み取り専用接続で `sessions` と `events` を確認する。セッション内は `seq` 順、対応する開始/結果は `request_id` で結ぶ。`elapsed_ms` は実際のイベント時点、`written_ms` はバッチ保存時点なので同一視しない。保存キャンセルを「保存失敗」へ、保存準備成功を「ディスク書込み成功」へ読み替えない。

## 検証・制約

BGM/ボイス/SE OFFでローカル検証。Windows実UI、実GPU、本人PCは対象外。既存のexport templatesが見つからず、release実バイナリの書き出し/起動は未検証。release判定分岐のテストと実release試験を区別する。

根拠: [Godot OSの公式API](https://docs.godotengine.org/en/stable/classes/class_os.html)、[SQLiteのロックとrollback journal](https://www.sqlite.org/lockingv3.html)。後者は異常終了時のhot journalと複数プロセスのロックを説明している。

読み取り用SQL例（DBへの書込みは不要）:

```sql
SELECT session, version, started_ms, updated_ms, clean_closed
FROM sessions ORDER BY started_ms DESC;
SELECT seq, elapsed_ms, request_id, kind, op, ok, duration_ms, data
FROM events WHERE session = :session ORDER BY seq;
```

保持上限で古いイベントが削除されるため、古い要求の開始と終了の片方だけが残る場合がある。正常終了フラグは全イベントの完全性保証ではない。匿名人物番号やsalt付き装備参照はセッション内で照合するためのもので、別セッションの同じ番号を同一人物とは扱わない。
